# R23.3 — 過去の復旧例の照合とメモリ要求捕捉経路の修正

2026-11-21。R21.3はユーザーの再ビルドでMEM/MR4/RUNALL・スペースマンボウPLAYが成功。一方、I/O削除比較版R23.2では `EZ80MEM P1:FAIL stage 0 ADDR=07FFFE EXP=31 ACT=7E` と報告された。

## 過去の成功例を先に照合した結果

| 成功へ戻った版・対策 | 実際の変更 | R23.2との照合 |
|---|---|---|
| MSX16bit / 拡張24bitバス分離 | 拡張周期のMSX側アドレス・MREQを遮断。下位FFFFの誤到達を防ぐ | ラッパのRequest_MSX_AddressとブリッジのMSX遮断に残っている |
| 要求時のアドレス・データ保持 | ラッパでRequest_Address/Request_Dataを保持し、ブリッジでも物理アドレス・データを保持 | 既に含まれる。データはT1/T2で更新されるため、アドレスと同じ最初のエッジで常に最終値とは仮定しない |
| R18.3 | RST開始要求をT3でFrame_Rst_Pendingに登録し、T4で使用。実機でMEM/RW2/RS8/RUNALLが復旧 | CPU内の登録処理はR23.2にも含まれる。再移植する欠落はない |
| R21.2 | ブリッジのW/R記録、ラッパ読出しとtop接続を追加。状態遷移・WAIT・SDRAM制御は維持 | その後MEM等がPASSしたが、機能修正で原因を除去したと証明されたものではない |
| R21.3 | 観測byte選択をVerilogのcaseへ移し、Trace_Select/Dataを明示接続 | R23.2はこの版を基準にしており、接続修正は残る |
| R22.4 | 内部捕捉・SDRAMコマンド・DQ・返答の観測を追加。実機でMR6/MX6/MEM/RUNALLがPASS | 新I/O実行制御と観測追加による配置変化を区別できていない。観測回路を移植すれば直ると扱わない |

過去のPASS例は重要だが、その版の観測回路を再追加して配置を変える方法を恒久対策にはしない。今回不足していたと確認できる旧修正は見つからなかった。

## 今回選んだ捕捉経路

R23.1の実配置には、`cpu1/WR_n_i_s0/Q`から`memory_bridge/ram_din_2_s0/CE`等へ **−4.005ns** のSetup違反がある。54MHz立下りから立上りへの半周期9.259nsに対し、データ経路13.226ns、配線10.432ns、論理2.562ns、clock-to-Q 0.232ns。制御条件を計算してからペイロードFFのCEへ届く経路である。

R23.2のimplは未提供なので、この値をR23.2の測定値へ流用しない。この経路は実機不一致に関係する候補であり、ACT=7Eだけから原因確定はしない。CPU上流や通常SDRAM側の別の違反も残り得る。

以前「最悪Setup」と記したPath1の値は、レポートのPath1値である。表示400経路すべての最小Slackとは一致しない。R21.3の表示400経路には−8.803ns、R23.1には−6.465nsの経路があり、レポートの先頭値だけで全体の最悪を比較しない。

## FPGA変更はブリッジ1ファイルだけ

基準はR23.2。`fpga/src/ez80_memory_bridge.v`だけを変更する。

- 54MHz立上りでMREQ、RD、WR、拡張窓を4個のFFへ連続捕捉する。CPUのCEで間引かない。
- 次の54MHz立上りで、捕捉済みの周期種別から要求を一度だけ受理する。
- 受理時に物理アドレス・データを既存ram_addr/ram_dinへ保持する。write属性とW記録にも同じ捕捉済みWRを使う。
- 現在のMREQと拡張窓を受理条件にも残し、捕捉後に撤回された周期を誤って要求にしない。
- 先行WAITは従来どおり現在のMREQ/T1から組合せで発生させる。WR捕捉やram_reqまでWAITを遅らせない。
- COMPLETE、DRAIN、doneの同期、CPUへの返答、MSX側遮断、SDRAM/VDPのスケジュールは変更しない。

CPU本体、マイクロコード、分類関数、ラッパ、レジスタ、SDRAM制御、top、GPRJ、CST、SDCはR23.2とバイト一致。I/O4命令のED-NOP化は維持する。レジスタ24bit再構成・FF化や、残す5命令の追加は行わない。

### 有効エッジと保持期間

| 時点 | 処理 | 保持・確認条件 |
|---|---|---|
| T1 | ラッパがアドレス/窓を保持しMREQを発生 | 先行WAITを直ちにLowへ。RD/WRがまだ無効でも要求は受理しない |
| T2のCPU立下り | WRが有効、ラッパの書込データが最終化 | 既にWAITが出ているためCPUは未完了周期を終了しない |
| 次の54MHz立上りE0 | 制御4bitを単純なFFで捕捉 | 元の半周期経路を、まず各FFのDまでにする |
| 次の54MHz立上りE1 | 捕捉済み周期で要求/ペイロードを受理 | 制御FFから受理FFまでは1周期18.518ns。CPUアドレス/データはWAITで保持 |
| 受理〜done | 既存ラッチを保持しSDRAM側へ渡す | ram_req、アドレス、データ、write属性を維持。再受理しない |
| COMPLETE | 返答を保持してWAITを解除 | 元のCPU取込・DRAIN手順を維持 |

E0以前には制御以外の組合せ経路を増やさない。E1まで受理を遅らせるのはプロトコル上の変更であり、multicycle指定ではない。GOWINが実際に満たすかは、受理FFのD/CEおよび新しい4FFのD経路を配置後に確認する。

短いMREQ/窓の経路は受理条件に残る。単にすべての経路がフルサイクルになったとは主張しない。MREQはWRより早いT1で確定すること、読出しでもWAITで完了まで保持されることをCPUモデルと試験で照合する。

## 検証

`verification_r23_3/summary.json`に新CPUと今回のVerilogを使った結果を保存する。

- ブリッジの4構成（従来/事前判定窓、bank修飾有無）：全256バンク、境界を含む8オフセット、読書き、I/O/refresh/IACK、完了・重複防止、リセット。計40960チェック。
- 捕捉位相48ケース：010100、07FFFE、07FFFF、080000、0A6000、010101/102/103、31/CE、ストローブ位相変更。T1の先行WAIT、最終データの捕捉、ペイロード保持、done高止まり中の次要求・DRAINを検査。
- MREQなし4096クロックで偽WAIT/偽要求なし。捕捉後のMREQ撤回とリセットで古い要求を再発行しないことを検査。
- EZ80MEMの9条件、MR4の8条件、IONの7条件を実COMで回帰。故障注入・対応識別・/RUNなし等の期待終了を含む。
- EZ80IM0実COMは通常とCE停止の2プロファイルで、割込みフレームのメモリ書込み・読出しも回帰。
- VHDL-93の6ファイルを解析。

これは配置後遅延の検証や、実機7E不一致の再現ではない。GOWINはこの環境では実行していない。4個のFF追加がRTL上の増分だが、実際のRegister/LUT/CLS差は合成結果で判断する。

## 実機の手順

1. 新規フォルダへ展開し、`fpga/project_eZ80/MSXNanoTang20K_eZ80.gprj`を合成・配置配線する。
2. 新しいイメージを書き込み、電源を入れ直す。
3. **最初にEZ80MEM /RUNを単独実行**。失敗ならStage/ADDR/EXP/ACTを保存し、そこで止める。
4. MEMがPASSならEZ80MR4 /RUN、EZ80ION /RUN、EZ80IM0 /RUN、RUNALL.BAT。
5. 全PASS後、SOFARUNからスペースマンボウを起動してPLAY。
6. Logic/LUT/CLS/Registerとimplを保存し、新しい制御捕捉FFおよび受理CEの経路を確認する。

新しいCOMは不要。既存COMはすべてバイト不変。正常表示はMEM P1、MR4 R21.3、ION R23.1、IM0 R19のままでよい。IONはCRC32 89950529。

本版は実機復旧を保証する版ではない。MEMの不一致が続く場合、同じ修正を積み重ねず、MR4のW/RとR23.3のimplで残る捕捉経路を確認する。マルチサイクル指定や一律の制約緩和は追加しない。
