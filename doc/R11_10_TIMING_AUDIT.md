# R11.10 タイミング監査と命令実装再開の区切り

2026-11-06 JST。対象はMSXnano T80への公式eZ80命令拡張。独自KC160風モード案とは分ける。

## 結論

R11.10のFPGA回路、制約、COMを変更しない。実機確認済みR11.10を機能開発の基準として保持する。今回はタイミング監査と追加シミュレーションまでを区切りとし、次の機能追加は工程8のMBASEから再開する。STA達成や最終完成とは扱わない。

全体の配線最適化を繰り返す作業はここで区切る。命令追加後も機能回帰とGOWIN評価を継続し、実機FAIL、配置不能、または測定した捕捉間隔を満たさない条件が出た場合は原因対処を優先する。ゲーム動作の成功だけでSetup／Holdが安全とは判断しない。

## ユーザー実機確認

GOWIN成功、Logic86%。EZ80MEM /RUNはP1: PASS。RUNALLはEZ80LDH／EZ80LDX／EZ80MAD／EZ80MB／EZ80MIX／EZ80TSTの6本がP2: NOT READY、それ以外PASS。SofaRunからスペースマンボウを起動してプレイできた。

## 捕捉条件の確認

| 経路 | RTL上の捕捉 | 今回の判断 |
|---|---|---|
| MCycle→RD／要求保持 | MCycleはcore ClkEn有効の54MHz上昇で更新。RDと要求レジスタはclk_falling有効の下降で捕捉 | テストの有効エッジ間隔を測定。9.259nsの静的な半周期だけが実際の間隔とは限らない |
| IR等→Upper | Upperはリセットまたはcore ClkEn有効の上昇で更新 | 有効エッジ間隔が長い条件はあるが、全組合せ入力や物理Holdの証明ではない |
| VDP→SDRAMシーケンサ | VDP DHは27MHz上昇で更新。ff_sdr_seqは108MHz上昇ごとにDHを参照 | CPUの間引きとは独立。CPU CEを理由に除外できない |

Topのclk_enable_3m6_54とclk_falling_3m6_54は、外部ex_bus_clk_3m6をPINFILTERと54MHzレジスタで取り込んで生成する。ENABLE_WAIT時は両方をwait_ioでゲートする。固定DIV=16が外部入力に対して常に成立する保証は現在のGPRJ／SDCから得られない。

RD先頭報告はMCycle_1_s0/Q→RD_s0/D、54MHz上昇→下降、関係9.259ns、データ15.890ns、Slack−6.663ns。最悪報告のUpper経路はIR_6_s0/Q→UpperのCE、関係18.518ns、データ25.733ns、Slack−7.250ns。実際に使わない捕捉エッジを除外するには、始点・終点ごとの安定条件と有効化条件の証明が必要であり、今回例外は追加していない。

## 追加した実CPU試験

verify_capture_r11_11.pyはR11.10の実コア・ラッパをGHDL変換し、実COMを実行する。RTLへ変更を入れず、シミュレーション用の観測器だけを変換後コードへ追加する。時間単位20nsの試験クロックで測った周期数を54MHzへ換算している。実機の遅延注釈やSDFシミュレーションではない。

| ケース | 有効下降エッジ数 | MCycle変化→下降捕捉 最短 | IR変化→core有効上昇 最短 |
|---|---:|---:|---:|
| ['control_r10', 4, 1, 7] | 93222 | 1.5周期 | 4.0周期 |
| ['irq_r11', 4, 1, 7] | 10457 | 1.5周期 | 4.0周期 |
| ['control_r10', 16, 0, 3] | 82029 | 7.5周期 | 16.0周期 |

DIV4のMCycle最短1.5周期は54MHz換算27.778ns、DIV16の7.5周期は138.889ns。IR側は4周期または16周期。ただし測定対象の始点はMCycleとIRであり、すべてのアドレス・制御・演算データが同じ期間安定するとは主張しない。Upper64bitがcore有効エッジ以外で更新されないことも監視した。

正常3ケースと、捕捉直前にMCycleを変える故障1ケースを実行した。故障は捕捉間隔検査で検出された。R11.10の254正常ケース＋16故障検出は既存結果として参照し、今回全件を再実行した数字には加算しない。

## Holdの残課題

先頭報告はvdp4/u_v9958/n1524_s1/Q→mem1/n1032_s0/D。合成netlistでは終点n1032_3がSDRAM DQのbit3／11／19／27へ接続され、書込みデータ出力FFであることを確認した。この先頭経路をDH→シーケンサと同一視しない。27MHz上昇→108MHz上昇、関係0ns、クロックスキュー−3.599ns、データ0.567ns、Slack−3.078ns。R11.9の先頭Hold−2.727nsより悪化した。

別のHold経路としてDH→ff_sdr_seq_1/2が−2.432ns、DH→ff_sdr_seq_0が−2.374ns、DL→SdrStaが−2.483nsなど報告される。全42違反端点に対し詳細表は25経路の報告で、残りの全内訳は未取得。書込みデータFFの捕捉が出力無効期間である可能性はあるが、その条件と次の有効書込み前の上書きは今回証明しておらず、無視しない。

入力側へ同期FFを足すだけでは、ff_sdr_seqの開始位相やVDP／CPUスロット境界が変わり得る。VRAMの読出しデータ保持・SDRAMコマンド列を含む検証が必要なため、今回は変更しない。VDP優先、競合時CPU WAIT、既存VRAM配置を維持する。ここは未解決として残し、タイミング達成・製品品質の保証はしない。

## MBASE実装へ戻るための準備

公式eZ80のLD MB,A（ED 6D）／LD A,MB（ED 6E）はADLモードの命令で、Z80モードではNOP。フラグは変更しない。MBASEは短いアドレスへ上位バイトを供給するため、単純な8bitレジスタ転送の追加だけでは完成しない。

参照：ZiLOG eZ80 CPU User Manual UM0077、LD MB,A／LD A,MB、Memory Modes。公式配布URL https://www.zilog.com/docs/um0077.pdf 。確認用のZiLOG著作マニュアル写し https://media.digikey.com/pdf/Data%20Sheets/ZiLOG%20PDFs/eZ80%C2%AE%20CPU%20User%20Manual.pdf 。写しは旧版UM007712-0503のため、実装時は対応する新版の記述とも照合する。

次の機能追加で実施する項目：

1. MBASEリセット00、ADL限定の転送とフラグ不変を実装。
2. Z80フェッチ、短いデータ／SPSアクセス、境界ラップ、JP復帰との関係を命令別に整理して反映。
3. 16bit MSXバスと24bit物理要求を分離したまま、MBASE非ゼロ時もMSX側FFFFhへ漏れないことを検証。
4. 通常I/O・IACK・refreshとメモリアクセスのバンク選択を別に確認。CPU内のアドレス形成とラッパの互換空間遮断を混同しない。
5. 既存EZ80MB.COMで試験できる範囲を確認し、全要求を満たしてから診断機能ビットを有効化。今回EZ80MBはまだNOT READY。
6. テスト中はDOS／BIOSを呼ばず、MBASE=00とZ80状態へ戻してから結果を表示。メモリ不一致はアドレス・期待値・実測値を表示。

MADL／混在フレームはこの後に分けて実装する。上位I/Oアドレスを0固定する追加I/O命令は実装対象に戻さない。

## 配布と再現

これはR11.10への監査資料追加で、新CPU版や新bitstreamではない。GOWINの再ビルド、COMのFLASH書込み直しは不要。

ZIP内のtools/verify_capture_r11_11.pyをR11.10展開先のtoolsへ置き、同じプロジェクトを使って実行する。GHDL／IVERILOG／IVL_ROOT／VVPを環境変数で指定できる。標準入口はpython3 tools/verify_capture_r11_11.py。verification_capture_r11_11_result.jsonは使用した全FPGAソースのSHAを含む。verification_capture_r11_11の4ログに正常3件と故障1件を収録する。
