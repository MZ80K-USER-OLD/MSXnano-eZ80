# eZ80 restart R20.5 — SDRAM要求保持の修正候補

## 現状

R20.4の実機ではEZ80SL4とEZ80RF4がCASE 0で停止し、SLPを実行しないEZ80SP0もADDR=0A6004 EXP=3E ACT=31で失敗しました。R20.2では同じSP0がPASSしています。

R20.4の合成ネットリストではDiag_SLP_WakeのFFが残り、D6で立つことと、CPUのCEでSleep_FFを0へ戻すLUT論理を確認しました。配線だけの問題は解消していますが、実機停止の原因は未確定です。

R20.5は、SDRAM要求保持の経路を変更した候補版です。GOWIN合成・配置配線・実機は未確認です。修正完了やタイミング達成と判断していません。最後の全体実機確認済み基準はR19.1です。

## 変更の根拠

今回のR20.4レポートでは、Request_Extended（54MHz立下り）→MSXアドレスの遮断→MegaRAMデコード→sdram_seq（54MHz立上り）という経路が、9.259nsの半周期に対しslack -5.347nsでした。CPUのCEで保持される内部デコード経路とは区別して調査する対象です。全体のFmax24.023MHzだけで実機不良の原因とは判断していません。

従来は、状態0で要求を見て状態1へ進み、状態1で要求元・アドレス・データを取得していました。要求受付とペイロード取得が別のタイミングであり、状態回路も要求元の組合せデコードを直接参照していました。

## R20.5の変更

FPGAの変更は `fpga/src/memory_ez80.v` だけです。

1. 状態0かつ受付可能な映像位相で、54MHz立下りに要求元・アドレス・書込データ・書込指定を一緒に保持します。
2. 立上りの状態0は、保持済みの受付情報だけを使って状態1へ進みます。映像位相が受付枠を過ぎていれば次の枠を待ちます。
3. 状態1は保持済みの書込指定で起動します。ここでは生のCPUデータやMapper/MegaRAM選択を取り直しません。
4. 完了後の状態4も、立下りに採取した要求解除情報を参照します。

既存のアドレス・データ・要求元レジスタを再利用します。新しい制御FFは論理上3ビット（受付有効・要求解除サンプル・書込指定サンプル）で、大きなペイロード複製、タイマ、RAMを追加しません。実際のLUT/FF数はGOWINで測定が必要です。

CPUラッパーが立下りに出す要求から、今回の要求採取までは同じ極性間の1周期を使う構造にします。従来の半周期内で長いデコードと状態遷移をまとめる経路を分割する目的です。新しい経路のタイミングは再配置配線後に確認が必要です。

CPU、SLP解除回路、拡張メモリの四相ハンドシェイク、MSX 16bit/拡張24bitバスの分離、GPRJ、SDCはR20.4から変更しません。制約緩和や一律マルチサイクル指定は追加しません。

## 互換性と検証

受付直前に要求が来る位相では、次の受付枠まで待つ場合があります。そのため、旧memory.vとのCPU側SDRAMピン完全一致比較は一部位相で不一致になります。この比較をPASSと扱っていません。

代わりに、次を独立に確認します。

- MapperとMegaRAMの書込・読出し、全4バイトレーン、境界またぎ、同時要求時のMapper優先。
- 受付後に入力アドレス・データ・書込指定を変えても、保持した要求が変化しないこと。
- 受理途中のリセット後に要求が残らず、再度読み書きできること。
- VDP枠のSDRAMピンを元のmemory.vと4位相で比較すること。
- 既存のメモリ、割り込み、ロック状態、SLP/REFのCOM回帰。
- 同じEZ80SP0.COMの実COM実行と、0A6004への故障注入時にADDR/EXP/ACTが表示されること。

要求保持の単体試験は4位相×通常/入力変更×立上り/立下り後の要求開始の16ケースとリセット1ケースです。入力変更は保持契約を調べるための人工的な試験であり、実機故障の再現ではありません。100/50/25MHzへ比例縮小したモデルで測定した最大要求開始→結果保持時間は290nsでした（同モデルのCPU 1T=300ns未満を検査）。実機の全条件を保証する締切証明ではありません。

VDP枠のピン比較は4位相で実施します。CPU側の全ピン一致とは別の確認です。詳細ログと集計はverification_r20_5に収録します。

モデルには簡略DOS、PINFILTERのZ値保持、タイマ短縮、配置配線遅延がない等の制限があります。SL4/RF4の16ケースのうち追加2ケースはCPUの30分周比も合わせています。ローカルPASSで実機修正済みとは判断しません。

## ビルドと実機確認

`fpga/project_eZ80/MSXNanoTang20K_eZ80.gprj` を使います。旧implは退避し、合成から配置配線まで再実行してください。出力implで、旧Request_Extended→sdram_seq直結経路がなくなったか、新しい採取レジスタへのsetup/hold、採取後から受付までの経路を確認します。LogicとFmaxも再測定します。

新しいimpl ZIPを送ってください。実機では次の順に確認します。

1. 再起動後 `EZ80SP0 /RUN` → `EZ80SP0 R20.3 PRE-SLP: PASS`。
2. `EZ80MEM /RUN` → `EZ80MEM P1: PASS`。
3. 両方PASSなら `EZ80SL4 /RUN` → `EZ80SL4 R20.4: PASS`。
4. SL4もPASSなら `EZ80RF4 /RUN` → `EZ80RF4 R20.4: PASS`。
5. 上記が通過したらRUNALL.BAT、SofaRunからスペースマンボウの起動・PLAY。

停止時は最後のCASE番号を記録し、再起動してください。SP0/MEMがFAILなら、そのstageとADDR/EXP/ACTを優先し、SLPテストを繰り返す必要はありません。

## COMの配布

新規COMは作っていません。R20.4の34本をバイト単位で維持し、既に配布済みのSP0をそのまま加えた35本を同梱します。FLASH上の既存COMを更新する必要はありません。出力バージョンがR20.3/R20.4でも正しい表示です。

| COM | バイト数 | CRC32 |
| --- | ---: | --- |
| EZ80SP0.COM | 5124 | A3489B41 |
| EZ80SL4.COM | 5178 | 5B66BD02 |
| EZ80RF4.COM | 3537 | 2612A915 |

DOS/BIOSがEIすることを想定した表示前のZ80状態復元・拡張ロック、表示後のDIは既存COMのままです。メモリ不一致のADDR/EXP/ACT表示も維持します。

新しい保持回路と既存回帰を合わせ、ローカル101ケースを確認しました。READY/NOT READY/故障検出等の期待結果も含みます。CPU内部全命令の網羅検証を意味しません。旧全CPUピン比較の不一致はこのPASS数に含めず、別ログに保存しています。旧 `verify_legacy_refresh_r20_1.py` は旧波形完全一致の履歴用であり、R20.5の合格判定には使いません。
