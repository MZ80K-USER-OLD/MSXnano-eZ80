# R11.5：診断用ベクタ窓と要求信号の保持

## 実機確認済みの基準 R11.4B

ユーザーはR11.4BでEZ80MEM P1: PASS、RUNALLの実装済みテスト全PASS、未実装6本のNOT READY、SofaRunからスペースマンボウの起動・プレイを確認した。
R11.4Bを基準として維持する。R11.3は07FFFFhで52h→D6h、R11.4Aは080000hでA6h→73hの不一致が出た。
AのADDR=000000という報告は080000の入力間違いと訂正された。診断表示そのものの破損が確認されたわけではない。
Bで改善した結果はSDRAMの捕捉経路の関与と整合するが、A/Bは配置配線も変わるため、単一の物理原因を証明した結果とはしない。

| 項目 | R11.4BのGOWIN実測 |
|---|---:|
| Logic／LUT | 17,766（86%）／15,568 |
| Register／CLS | 7,310／9,718（94%） |
| BSRAM | 43/46 |
| Fmax 108／54／27MHz系 | 173.734／41.663／74.566MHz |
| Setup／Hold違反端点 | 656／43 |

元レポートはimpl(4).zip。SHAと数値はR11_4B_GOWIN_BASELINE.json、PnR原文・タイミング集計とPath1詳細も同梱する。
108MHzの同一クロック内SetupはBで解消したが、異なるクロック間のHoldなどが残っており、設計全体のタイミング成立ではない。

## CPU側の半周期経路

レポートのPath1はXY_State→EX_SP_Index→マイクロコードWrite→診断用ベクタ窓判定→Request_MSX_AddressのD。
54MHzの上昇→下降で関係9.259ns、データ遅延11.969ns、Slack−2.742ns、8段。データ経路の約70%が配線遅延だった。
診断用ベクタ窓のために、生のWriteデコードが多数のアドレス保持FFへ入る構成になっていた。

R11.5は次のように保持点を分ける。

| 保持する情報 | 内容 |
|---|---|
| Request_Address | 通常の24bit要求。I/O・IACKの資格条件は従来どおり |
| Request_MSX_Address／Request_Extended | 通常のMSX側遮断済みアドレスと拡張要求フラグ |
| Request_Write／Request_IO | 同じT1下降で受け取る要求方向 |
| Request_Vector（新規） | 診断有効・バンク00・0000〜007Fh・メモリ・通常読出し候補となる要求の印 |

候補判定にはWriteを入れない。保持後のRequest_Vector AND NOT Request_WriteでVector_Read_Requestを作り、診断の読出しだけ0Fバンクへ振り替える。
診断中の書込みは従来どおりMSX側を使用する。読書きの意図・候補・アドレスは同じ要求捕捉点で保持し、WAITやCEN停止中に上流の意図が変わっても更新しない。
診断読出しを振り替える場合はMSXアドレスを0000hへ遮断し、拡張要求を立てる。リフレッシュ出力の優先順位は従来どおり。

これによりWriteをアドレス保持FFの入力条件から外す。Write→Request_Write自体の経路は残る。
また、保持後のVector_Read_Requestから実アドレス出力・ブリッジへ至る新しい経路も評価が必要。全体のFmax改善やLUT削減を保証する変更ではない。
全デコードを実行部から分離したものでも、新しい命令の追加でもない。

## 要求信号のクロック間受渡し

Bの最悪Hold報告はmemory_bridge/ram_req→mem1/ext_meta、−2.948ns。54MHz上昇→108MHz上昇の同時エッジ関係に、3.599nsのクロック経路差が計上されていた。
Bで実機確認済みのpayload用下降サンプルと同じエッジに、要求信号のext_req_sampleを1bit追加する。

1. 108MHzの下降で要求をext_req_sampleへ受ける。
2. 次の上昇でext_meta、次の上昇でext_syncへ進める。
3. 空き条件を確認しアームする。
4. アーム後の下降サンプルを、次の上昇で取引保持レジスタへ移し、pendingと同時に公開する。
5. payload・要求は送信側で応答受領まで保持し、受理後も取引保持値を次の取引まで保つ。

最初の下降要求サンプルを基準にすると、資格のあるpayloadサンプルまで3受信周期、取引の公開まで3.5受信周期。
108MHzでは約27.78ns／32.41ns。受信待ち時間は増えるが、既存のWAIT・4相ハンドシェイクで吸収する。IRQの命令境界やCPUの命令シーケンスは変更しない。
SDRAMの後段はBと同じ上昇エッジの取引保持値を使用し、半周期の複雑な制御を再導入しない。

同期器入口へ至る直接の同時上昇エッジ経路を変更するが、送信上昇→受信下降、受信下降→上昇のSTA確認は必要。
これはメタスタビリティの物理試験でも、PLL／CLKDIVのクロックモデルが正しいことの証明でもない。

## 16bit／24bitの分離とFFFFh

CPUの24bit拡張メモリ経路とMSX用16bit経路は分離を維持する。
非ゼロバンクの通常メモリアクセスは、スロット判定より上流でMSXアドレス0000h、MSX側MREQ無効にする。
スロットレジスタは上位バンクを見ず16bitだけでFFFFhを判定するので、アドレス遮断とMREQ遮断の両方を維持する。
バンク00のFFFFh、I/O、リフレッシュの正規動作は残す。

トップのスロット回路は変更しない。実際のトップから抽出した判定・更新処理をCOM試験へ組み込み、遅延した読出し要求・書込み要求と値の変化を監視する。
07FFFFhをMSX側へ漏らす読出し・書込み故障の2条件で監視が検出することを確認する。

## 検証と限界

- 現行RTLで236条件の回帰と11条件の故障検出を確認する。最終値はverification_result.json。
- 要求保持単体は診断あり／なしの各86,016チェック。全256バンク、8オフセット、診断読出し・診断中の書込みを含む8種別、WAIT、CEN停止、リフレッシュを確認する。
- 上流のWrite・Diag_Activeなどを捕捉後に変えても、保持済み要求を変えないことを確認する。
- 書込み意図を誤って読出し扱いにする故障を追加し、診断窓への誤転送を検出する。
- CDCは送信側位相4条件、SDRAM起動待ち1条件、旧コントローラとのピン一致4条件。早過ぎる公開とpayload破壊も検出する。
- 実COM、IRQ／IM2／NMI／RETI／RETN、WAIT・CEN停止、バンク境界、旧T80との条件分岐比較、EX(SP)、VDP競合・リフレッシュ等を維持する。
- 2ファイルの再生成、VHDL-93解析、122プロジェクト参照、元G80Aの一致、先行COM20本の完全一致を確認する。

検証中に容量不足で一部が中断したため、中間出力を整理して未完了の試験を再実行した。完了済み群は保持し、最終ログ・集計は有効な実行結果で構成する。

GOWIN合成・配置配線・資源量・R11.5の実機・全MSX BIOS/DOS起動・全FUSEはこの環境では実施していない。
理想RTLのPASSを、物理タイミングの成立や実機の不一致解消の保証とはしない。

## 残す課題

SDC、CST、GPRJ、トップ、ブリッジ、CPU本体・マイクロコード、VDPはBと同一。タイミング例外の追加・緩和はしない。
VRAM→VDPの報告経路（−4.666ns）、旧メモリ経路のクロック間Hold、PR1014の一般配線、VDPのhdmi_reset警告は今回の変更で解消したと扱わない。
